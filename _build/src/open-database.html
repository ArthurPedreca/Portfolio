Client records readable with the public key

A booking platform built with an AI tool looked finished. Behind the polished interface, anyone holding the app’s public key could read its clients, appointments and payments.

Summary

The platform was getting ready to launch. In a Supabase app the public key ships to every visitor’s browser by design, so it is not a secret. The only thing standing between that key and the data is the set of row level security policies on each table, and the access rules on each storage bucket.

Here those rules were open. Four tables and every storage bucket answered to the public key alone, with no login. All five were closed before a single real user signed up.

Status updates

  1. Resolved

    Every table and bucket now refuses the public key on its own. Closed before launch.

  2. Fix

    Each table got a role-based policy that limits rows to the business they belong to. Every bucket went private, with files served through signed URLs that expire.

  3. Identified

    With only the public key and no login, clients, appointments, payments and intake_forms returned every row. Every storage bucket was public.

  4. Investigating

    Tested every table and bucket the way an outsider would: no password, only what any visitor’s browser already has.

Root cause

The policies were written so the app would work, not so each business’s data stayed separate. A rule like using (true) makes a table readable to anyone, and nothing looks wrong from the inside, because the interface only ever asks for what it is about to show.

This is the most common hole I see in apps built with AI tools. The screens are right, the demo is right, and the database is wide open.

The fix

policies/clients.sql · simplified
create policy "read clients" on clients for select-  using (true);+  using (business_id in (select my_businesses()));

The same pattern went onto the other three tables. For files, the buckets were made private and the app now asks for a short-lived signed URL when it needs to show one.
